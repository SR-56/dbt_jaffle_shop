# ADR-0003: AI は指標に加えて、公開モデルへの読み取り専用 SQL も使えるようにする

- 状態: 採用
- 日付: 2026-11-18
- 関連: ADR-0001, ADR-0004（公開の範囲の決め方を置き換え）

## 背景

当初、AI（Claude Code）は `mf query` だけで答えることにしていた。これでは、指標として定義されていない分析（顧客ごとの注文回数の分布、一緒に買われる商品、コホートなど）ができない。

ユーザーが役割を次のように決めた。

- 指標の定義は MetricFlow を唯一の定義元（SSoT）にする。AI とダッシュボードは同じ指標から同じ数字を出す
- ダッシュボードは、選んだ指標（saved query）の表示に専念する
- AI は saved query に縛られず、より柔軟な分析をする。ただし参照できるのは、公開したモデルとコンテキストだけ

## 検討した選択肢

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| A. `mf query` だけ（当初の方針） | 数字が必ず定義と一致する | 指標の外側の分析ができない。AI の価値が「ダッシュボードを自然言語で引ける」程度にとどまる |
| B. `mf query` + DuckDB に自由に SQL | 何でも分析できる | staging や seed まで見えてしまい、公開の範囲を決められない。指標を SQL で計算し直して数字がずれる恐れがある |
| C. `mf query` + 公開モデルだけに読み取り専用 SQL。公開の範囲は dbt の定義（`access: public` と YAML に書いた列）で決める | 指標の外側も分析できる。公開の範囲を dbt で管理でき、レビューできる | 定義済みの指標を SQL で計算し直すことは仕組みでは防げない（スキルの手順で防ぐ） |
| D. 公開モデルだけの DuckDB ファイルを別に作り、AI はそれだけを見る | 物理的に分かれていて分かりやすい | build のたびにファイルを作る手順が増える。C と守れる範囲は変わらない |

## 決定

C を採用する。

- 定義済みの指標の値は `mf query` で出す。saved query 以外の組み合わせでもよい
- 指標では表せない分析は、`scripts/public_data.py sql` で公開モデルに SQL を実行する
- 公開の範囲は、`access: public` のモデルの、YAML に書いた列。書いていない列は見えない（例: `dim_customers.customer_name`）→ **ADR-0004 で semantic layer（semantic_manifest.json）に置き換えた**
- コンテキスト（モデル・列の説明、指標、saved query）は `scripts/public_data.py context` で、dbt の manifest から出す

## 理由

- 指標の外側の分析こそが AI の価値なので、A では足りない
- B では「参照できるのは公開したものだけ」を守れない
- 公開の範囲を dbt の YAML に置けば、指標と同じく Git でレビューでき、説明（description）もコンテキストとしてそのまま AI に渡せる
- D は C と比べて守れる範囲が同じで、手順だけが増える

## 影響

- `public_data.py sql` は、公開する列だけをメモリ上の DuckDB にコピーし、元の DB を切り離してから、`enable_external_access = false` と `lock_configuration = true` を設定してクエリを実行する。2026-11-18 に確認: staging・非公開の列・time spine は「存在しない」エラーになり、seed の CSV の読み込み、元の DB の ATTACH、ファイルへの COPY、設定を戻す SET はすべて Permission / Invalid Input エラーになった。準備にかかる時間は約 0.1 秒
- SQL で出した `sum(order_total)`（671425.37）は `mf query` の `revenue` と一致した。ただし「指標は `mf query` で出す」はスキル（`.claude/skills/analyze-data/SKILL.md`）の手順で守らせているだけで、仕組みでは強制していない
- **仕組みで守れているのは `public_data.py` を通した場合だけ。** 同じリポジトリの Claude Code は開発にも使うので、seed の CSV やファイルを読む権限そのものは止めていない。分析専用の作業場所（公開モデルだけを置いたディレクトリと、権限を絞った設定）を分ければ完全に分けられるので、必要になったら見直す
- 同じ SQL の分析が何度も頼まれたら、指標や saved query に格上げする（AI の分析から、定義元に指標を足していく流れ）
- 列を公開するかどうかは、YAML に列を書くかどうかで決まる。列を足すときは、公開してよいかを考えてから書く
